# 交互模式手册

> 一句话总则：**交互必须服务于理解，不是服务于「看起来互动」。**

---

## 1. 为什么交互本身不够

两篇实证同时指向一个反直觉结论：

- **无引导的纯发现学习基本无效**（Kirschner, Sweller & Clark, 2006）。
- **但被动观看也无效**：ICAP 框架（Chi & Wylie）把认知投入分四档，学习效果 P（被动）< A（主动操作）< C（建构）< I（互动共创）。光点按钮看动画，只是 A 档。

所以真正有效的不是「有交互」，而是 **「有引导的高认知投入交互」**。

还有一个陷阱要防：**生成式 AI 天然倾向于减少摩擦**（直接给答案），而摩擦正是学习发生的地方。这叫「增强 vs 侵蚀悖论」。见 Kovshov et al., arXiv:2609.20738。

**推论**：课件的交互要**故意保留必要的认知摩擦**——先让你预测、先让你算、先让你找错，然后才给反馈。

## 2. 交互式知识呈现：五个原则与核心闭环

> **Sort Playground 是参考范式，不是模板。** 借它的「把抽象过程变成可观察、可操作、可验证的对象」，不搬它的排序算法、页面布局或视觉皮肤。

### 2.1 五个原则

| 原则 | 落地做法 | 反面例子 |
|---|---|---|
| **对象化呈现** | 抽象概念有可观察载体：卡片、节点、图形、数据块、空间模型 | 只有一段结论文字，或一张与操作无关的装饰图 |
| **动态过程** | 暴露中间状态：第 2 步执行后哪个量变了、下一步会怎样 | 一次跑完的动画，用户只看到开头和结尾 |
| **主动操作** | 拖拽、点击、输入、调参、单步、暂停、继续、重置 | 自动播放，用户只能看不能动 |
| **即时反馈** | 操作后立即用真实计算呈现状态、数值或后果 | 动画播完才出现一个与输入无关的结论 |
| **原理解释** | 把变化连回知识：为什么会这样，不这样会怎样 | 只显示对错，不解释机制 |

五个原则是一条链，不是五个模块：**对象被操作 → 状态发生变化 → 变化被反馈 → 反馈被解释。**

### 2.2 核心闭环

```text
预测 → 用户操作 → 状态变化 → 结果反馈 → 原理解释 → 迁移
```

**用户操作 → 状态变化 → 结果反馈 → 原理解释** 是不可省略的四环。

| 环节 | 要暴露什么 | 做不到的信号 |
|---|---|---|
| **用户操作** | 用户改的具体变量（角度、参数、输入、顺序） | 只有「下一步」按钮，操作没有信息量 |
| **状态变化** | 中间量、当前步骤、累计结果 | 画面变了但数值没变 |
| **结果反馈** | 与操作对应的真实结果 | 结果是写死的，或反馈与操作无关 |
| **原理解释** | 为什么变、规律是什么、边界在哪 | 只显示「对 / 错」或「完成」 |

**只做到「点一下、播一段动画」＝观看，不是交互。** 遇到这种情况，要么补上操作与反馈，要么降级成一张静态对照表。

### 2.3 选演示前先回答五个问题

1. **哪些知识适合可视化？** 有对象、有关系、有中间状态、有可调参数的适合；纯定义、纯结论、无可观察变化的不适合。
2. **用户可以操作什么？** 操作必须映射到一个真实变量，不能只是切换页面或播放。
3. **操作会改变什么？** 说不清「改了 X，所以 Y 变了」，就是装饰。
4. **如何反馈变化？** 用真实计算出的数值、图形或中间量，不用预设动画冒充结果。
5. **如何通过操作验证理解？** 让用户先预测再对照，或完成一个必须动手才能完成的任务。

**五个问题里有任何一个答不上来，就不要做演示。** 改成表格不丢人，硬塞动画才是负分。

## 3. 交互类型 × 学习任务对照表

| 学习任务 | 推荐交互 | 为什么 | 不要用 |
|---|---|---|---|
| 理解变量关系 | 滑块 + 实时结果 + 极端值标记 | 让人看到「拖到头会怎样」 | 静态公式截图 |
| 理解执行过程 | 单步执行 + 中间量显示 | 中间量是关键，只给结果等于没给 | 一次跑完的动画 |
| 理解空间关系 | 拖拽 + 辅助线 + 视角切换 | 空间关系必须自己动 | 一段录屏 |
| 学习程序实现 | 代码补全 / 输出预测 / 错误定位 | 预测先于运行，才有提取练习 | 直接给可运行代码 |
| 准备面试 | 先作答 → 再追问 → 按维度自评 | 面试考的是表达，不是选择 | 选择题 |
| 辨别相似概念 | 对照实验 / 分类 / 反例判断 | 差异必须在对比中显形 | 分别讲两遍 |
| 理解数量级 | 对数滑块 + 单位换算 | 人对大数无直觉，必须换算 | 「很大」这种形容词 |
| 理解概率/分布 | 抽样按钮 + 累积统计 | 让随机性自己显现 | 一条平滑曲线 |
| 理解算法执行 | 可视化对象 + 单步 + 暂停 + 重置 | 看到中间状态才能理解不变量 | 自动播完的排序动画 |

## 4. 四级优先级（选不出来时按这个退）

```
1. 真算的计算器     ← 用户乱填也有对的答案
2. 可拖的滑块       ← 看极端情况
3. 可点开的分步走   ← 看中间量怎么变
4. 静态对照表       ← 老老实实做表格
```

判断口诀：**能算就别画，能拖就别讲，能动就别静，能静就别编。**

第 4 级不是失败。**一张精心设计的对照表，比一个与目标无关的动画强十倍。**

## 5. Guided vs Buggy：按先验档位选练习形态

这是 knowvori 最需要严格执行的一条（C3）。依据：Tithi et al., CHI'26, arXiv:2602.16806，155 名本科生对照实验。

### 5.1 核心结论

| 学习者 | 有效形态 | 实验结果 | 为什么 |
|---|---|---|---|
| **低先验** | **Guided（填空式）** | 显著优于被动 worked example | 缺 schema，需要看到「完整解的骨架」，只填缺口 |
| **高先验** | **Buggy（找错式）** | 显著优于被动 worked example | 已有正确图式，才能识别「哪里不对」；找错带来更多探索-修正循环 |
| **低先验 + Buggy** | ❌ 无效 | — | 不知道对的长什么样，看不出错 |
| **高先验 + Guided** | ⚠️ 收益小 | — | 太简单，没有挑战 |

行为数据也支持：**Guided 组更多求助、更少错误；Buggy 组更多探索-修正循环。**

### 5.2 Guided 的做法（给零基础）

给一个**完整的解，但挖掉 1~3 个关键缺口**，用户要填。

```html
<div class="worked-step">① 计算点积 q·k₁ = <input data-answer="6"> </div>
<div class="worked-step">② 除以 √d：6 / 2 = <input data-answer="3"> </div>
<div class="worked-step">③ 对三个分数做 softmax → <span class="given">(已给出：0.09, 0.24, 0.67)</span></div>
```

设计要点：
- **缺口必须是「理解点」，不是「算术点」**。挖掉 softmax 比挖掉「6/2」有意义。
- 缺口不超过 3 个，否则等于让他从头做。
- 填错时给**指向缺口所在步骤的提示**，不要直接给答案。
- 每步右侧给一句「这一步在干什么」的一句话说明——脚手架不能全靠用户猜。

### 5.3 Buggy 的做法（给有基础）

给一个**看起来正确的解，埋 1~2 个真实的错**，用户要找出来并修。

```html
<div class="buggy-step" data-buggy="true">
  score = q · k / d      <!-- 埋错：应该是 √d -->
</div>
```

设计要点：
- **错必须是真实误解**，不是随机打错字符。见 `assessment-guidelines.md` 的误解库。
- 埋 1~2 个，不要 5 个——找 5 个错变体力活。
- 找出后要求**说明为什么错**，不只是改正。这一步才是建构（C 档 ICAP）。
- 允许「这里其实是对的」的判定——训练「不要疑神疑鬼」也是能力。

### 5.4 两者共同的硬要求

| 要求 | 说明 |
|---|---|
| **立即反馈** | 提交即判，不攒到最后 |
| **错误指向步骤** | 「第 3 步错了」而不是「答案错了」 |
| **可重来** | 能回到初始状态，不设次数限制 |
| **不打分** | 一旦打分就变成刷分，见 SKILL.md 第 7 节 |

## 6. 七种可直接复用的组件写法

### 6.1 真算计算器

```html
<div class="calc">
  <label>d = <input type="range" id="d" min="2" max="1024" step="1" value="4">
    <output id="dOut">4</output></label>
  <div class="result">最高权重：<b id="maxW">32.9%</b></div>
</div>
<script>
// 必须真的算，不许预置结果
function softmaxMax(d) {
  const scores = Array.from({length: 4}, () => (Math.random() - 0.5) * Math.sqrt(d));
  const m = Math.max(...scores);
  const exps = scores.map(s => Math.exp(s - m));
  const sum = exps.reduce((a, b) => a + b, 0);
  return Math.max(...exps) / sum;
}
</script>
```

**关键**：结果由函数算出，改参数就变。如果结果写死在 HTML 里，那就是假演示（违反 C6）。

### 6.2 滑块看极端

三个位置必须让用户能到：**最小值、默认值、最大值**。极端值往往才是理解的钥匙（比如 d=1024 时权重变成 100%）。

### 6.3 分步走

```
[上一步] [第 2/5 步：算分数] [下一步]
中间量：score = [3.0, 1.0, 0.5]
```
**中间量要一直可见**，不要只显示当前步的名字。

### 6.4 答后展开自测

```html
<div class="quiz" data-qid="q3">
  <p class="stem">题目……</p>
  <button class="opt" data-correct="false" data-why="你可能是把 d 当成了 √d">A</button>
  <button class="opt" data-correct="true"  data-why="对，因为方差随 d 线性增长">B</button>
  <div class="explain" hidden>要点展开……</div>
</div>
<script>
// 答错才展开，答对只给一行
</script>
```

### 6.5 对照实验

并排两个面板，同一操作同时作用，差异自己显形。适合「辨别相似概念」。

### 6.6 可复制代码块

```html
<pre><code id="snippet">...</code></pre>
<button onclick="navigator.clipboard.writeText(document.getElementById('snippet').textContent)">复制</button>
```
配 **预期输出**，让用户能自己核对。没执行过就标明「未运行」。

### 6.7 完成清单

```
[ ] 我能不看资料说出点积为什么表示相似度
[ ] 我能解释为什么要除以 √d
[ ] 我能手算 3 个词的权重并验证和为 1
```
**清单要能自查**，不是「我已学完」这种空话。

## 7. 交互的反模式（写下来防止手滑）

| 反模式 | 为什么坏 | 改成 |
|---|---|---|
| 装饰性动画 | 抢注意力，不承载信息 | 删掉，或改成有数值变化的演示 |
| 假数字演示 | 用户一改参数就露馅，教出错误理解 | 真算（C6） |
| 悬停才显示的关键内容 | 手机上根本看不到 | 改成点击/常显 |
| 一次给全部细节 | 认知过载 | 默认折叠，按需展开 |
| 「点击展开答案」按钮 | 大部分人会先点 | 答完才展开（C5 配套） |
| 计分 / 连击 / 排行 | 把学习变成刷分 | 只给对错与解释 |
| 无法重开的实验 | 试错一次就废了 | 必有重置 |
| 5 个以上的滑块 | 调不过来 | 降到 2~3 个 |
| 需要外部 CDN 的图表库 | 断网就瞎 | 手写 SVG 或 canvas |
| 只有最终答案没中间量 | 错了不知错哪 | 暴露中间量（Telemetry） |
| 自动播放且不能暂停 | 用户跟不上，也无法回看关键帧 | 加暂停 / 继续 / 单步 |
| 动画与数据不同步 | 看到的过程和真实计算结果对不上 | 动画只反映真实状态，不单独编排 |
| 为 3D 而 3D | 增加依赖和卡顿，与目标无关 | 能用 CSS/SVG 就不用 3D 库 |

## 8. 手机端的硬约束

用户经常在手机上看，这不是可选项：

| 项 | 要求 |
|---|---|
| 最小字号 | 14px（正文），12px（标注） |
| 触控目标 | ≥ 40×40px |
| 表格 | 超过 5 列必须可横向滚动，或改成卡片 |
| 长数字 | `overflow-wrap: anywhere` 或单独换行 |
| 滑块 | 拇指够得着，不要嵌在小格子里 |
| 悬停 | **完全不依赖 hover** 显示任何关键信息 |

## 9. 一句话检查表

写完每个交互，问：

1. 这个交互**教什么**？一句话说得出来吗？
2. 用户**能改什么**？改了以后**看到什么变**？
3. 这个变化是算出来的，还是预设的？
4. 乱填会崩吗？能重置吗？
5. 手机上能用吗？自动播放能暂停吗？
6. 删掉它，这节课会少学到东西吗？（答案是不能 → 删掉）
